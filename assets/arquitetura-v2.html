Inverted Agentic Orchestration

PADRÃO ARQUITETURAL · realizado neste repositório em Harness.Engine + Flows.Development

O agente de IDE (Copilot · Devin · Claude Code · Codex) atua como intérprete operacional: roda o harness, lê a próxima instrução no stdout, segue o contrato pedido e devolve uma resposta estruturada. Quem decide o próximo estado, valida respostas, persiste estado em disco e registra o rastro de execução é o harness — não o modelo.
Clique nos componentes para ver arquivos, responsabilidades e contratos do fluxo oficial do curso.

O PADRÃO — Inverted Agentic Orchestration
“A orquestração de agentes é invertida: quem decide o próximo estado é uma máquina de estados determinística em código — não o modelo.”

Intent — README.md

USE ESTE PADRÃO QUANDO
  • o workflow precisa ser reprodutível, auditável ou retomável;
  • a execução atravessa múltiplos passos e pode sobreviver a resets de contexto;
  • o agente precisa seguir contratos estruturados a cada turno;
  • o domínio exige validação determinística antes de avançar;
  • diferentes agentes de IDE precisam dirigir o mesmo protocolo;
  • tetos de passo, tempo ou custo precisam ser impostos pelo sistema;
  • a lógica de negócio do workflow deve ser testável fora do modelo.
EVITE QUANDO

A tarefa é uma geração única, sem estado, sem contrato de retorno e sem necessidade real de governar múltiplas iterações. Nesse caso, o harness só adiciona uma camada sem benefício.

BENEFÍCIOS
  • o workflow é testável como código comum;
  • a sequência de estados não depende mais da memória do modelo;
  • a execução pode ser retomada por outro agente, com os mesmos artefatos;
  • erros de protocolo são detectados cedo e tratados explicitamente;
  • guardas de passo, custo e timeout reduzem loops indefinidos;
  • o rastro persistido gera evidência para auditoria e avaliação posterior;
  • adaptadores diferentes compartilham o mesmo runner e contrato.
CUSTOS / TRADE-OFFS
  • o projeto precisa manter uma máquina de estados e contratos JSON;
  • cada domínio novo exige tasks, validações e prompts próprios;
  • a experiência depende da disciplina do agente em responder só no formato pedido;
  • workflows muito simples podem não justificar a camada de harness.

Definição: o agente da IDE executa as ações, mas a política do workflow vive fora do agente, em um harness determinístico que emite uma instrução por vez, valida respostas e persiste estado no filesystem. O loop "pensar → agir → observar" roda no driver; o harness é single-shot por turno. A máquina de estados decide o próximo comando e emite stop quando todas as features passam.

FLOW OFICIAL — desenvolvimento orientado a features

Flows.Development

Implementação incremental em 8 comandos: planeja, reorienta, testa a base, escolhe uma feature e implementa — verify e handoff rodam automaticamente dentro do implement quando há verify-feature.sh; só voltam ao driver como comandos separados se a automação faltar ou falhar.

start plan bearings smoke pick implement verify* handoff*

* fallback manual — o caminho normal já resolve dentro de implement

Agente Development

O agente customizado usa .harness/inbox.json, roda ./run-development.sh sem argumentos e reinicia contexto por feature.

.codex/agents/development.toml run-development.sh stop
sessão limpa por feature
CICLO POR FEATURE — quatro tempos que se repetem

Planejar

start → plan: cria init.sh, define alvo, comando de verificação e lista de features.

uma vez por run

Reorientar

bearings → smoke → pick: lê filesystem, roda smoke e escolhe a próxima pendência.

contexto limpo

Entregar

implement edita a feature; havendo verify-feature.sh, o harness roda auto-verify e, passando, auto-handoff (commit + progress.txt) sem gastar turno do driver. Sem script ou em falha, o driver responde verify (PASS/FAIL) e handoff (commit ou NO_GIT) manualmente.

commit + progress.txt por item

Parar

Quando FeatureStore.AllPassing() é verdadeiro, o stdout vira apenas stop.

sem decisão manual

SKILLS DO DEVELOPMENT
dev-initializer

dev-bearings
Reorienta com filesystem e histórico.
dev-smoke
Roda ./init.sh antes de editar.
dev-implement
Implementa uma feature por vez.
dev-verify
Fallback manual: executa verify_cmd/verify-feature.sh e responde PASS/FAIL quando a automação não rodou.
dev-handoff
Fallback manual: commita ou declara NO_GIT e atualiza progresso quando o auto-handoff falha.
